## 1. Core Web Vitals — CLS & LCP (56 URLs)

### Problem

Google Search Console reported **56 URLs** with two Core Web Vitals issues on **mobile**:

| Issue | Severity | URLs Affected |
|-------|----------|---------------|
| CLS (Cumulative Layout Shift) > 0.1 | Need improvement | 56 |
| LCP (Largest Contentful Paint) > 2.5s | Need improvement | 56 |

## Root Causes

### CLS > 0.1

**Primary cause:** Multiple `<Image>` components had `style={{ width: 'auto', height: 'auto' }}` which overrode the explicit `width`/`height` props. Browsers use these intrinsic dimensions to reserve space before the image loads — overriding them to `auto` caused layout shifts when images rendered at their actual size.

**Affected components:**
- `components/Hero.tsx` — 3 images (mobile fallback, mobile logo, desktop fallback)
- `components/Logo.tsx` — 1 image
- `app/products/ProductsPageClient.tsx` — 1 image
- `components/header/HeaderMobileIcons.tsx` — 1 image
- `components/header/HeaderRussianMobile.tsx` — 1 image
- `components/footer/Footer.tsx` — 1 image

### LCP > 2.5s

**Primary causes:**
1. Hero video had no `poster` image — browser had to wait for video to decode before painting anything in the hero area
2. No `<link rel="preload">` hints for critical above-the-fold assets
3. Blocking inline scripts in `<head>` were verbose (~70 lines) — unnecessary parse/execution time
4. No long-term cache headers for static assets

## Changes Made

### 1. CLS Fix — Remove style overrides on Image components

**Files changed:**
- `components/Hero.tsx` — Removed `style={{ width: 'auto', height: 'auto' }}` from 3 images, added `priority` to fallback images
- `components/Logo.tsx` — Removed `style={{ width: 'auto', height: 'auto' }}`
- `app/products/ProductsPageClient.tsx` — Removed `style={{ width: 'auto', height: 'auto' }}`
- `components/header/HeaderMobileIcons.tsx` — Removed style override, corrected width/height to match CSS (120x36), added `priority`
- `components/header/HeaderRussianMobile.tsx` — Removed style override, corrected width/height (120x36), added `priority`
- `components/footer/Footer.tsx` — Removed style override, changed `priority={false}` to `loading="lazy"`

**Why safe:** The visual rendering is unchanged — Tailwind CSS classes (`h-12 w-auto`, `object-contain`, `w-[120px]`) still control the rendered size. The only difference is the browser now correctly reserves space during load.

### 2. LCP Fix — Video poster image

**File:** `components/Hero.tsx`

Added `poster="/images/genosys-video-poster.jpg"` to both mobile and desktop `<video>` elements. This gives the browser an image to paint immediately while the video loads/decodes.

### 3. LCP Fix — Preload hints

**File:** `app/layout.tsx`

Added to `<head>`:
```html
<link rel="preload" href="/images/genosys-video-poster.jpg" as="image" fetchPriority="high" />
<link rel="preload" href="/images/genosys-logo.png" as="image" />
```

### 4. LCP Fix — Minified blocking scripts

**File:** `app/layout.tsx`

Minified the two blocking inline scripts (locale detection + theme initialization) from ~70 lines to single-line minified versions. Same exact logic, just reduced parse/execution time.

**Locale script behavior (unchanged):**
- Detects `/ar` and `/ru` URL paths
- Sets `lang`, `dir`, `data-locale`, `data-dir` on `<html>`
- Sets `dir`, `data-dir` on `<body>` (with MutationObserver fallback)
- Sets `window.__GENOSYS_DIR__` and `window.__GENOSYS_LANG__`

**Theme script behavior (unchanged):**
- Reads `localStorage('genosys-theme')`
- Checks `prefers-color-scheme: dark`
- Sets `data-theme` attribute and CSS class on `<html>`

### 5. Performance — Static asset cache headers

**File:** `next.config.js`

Added `headers()` configuration for long-term caching:
```

/Logo/*    → Cache-Control: public, max-age=31536000, immutable
/videos/*  → Cache-Control: public, max-age=31536000, immutable
```

## 2. Product Snippets — 236 Invalid Items

### Problem

Google Search Console **Shopping → Product snippets** reported **236 invalid items** with:
> "Either 'offers', 'review', or 'aggregateRating' should be specified"

Only **48 items** were valid (products with real prices on English product detail pages).

### Root Cause

Three components generate `@type: Product` JSON-LD structured data:

| Component | Used On | Had Offers? |
|-----------|---------|-------------|
| `ProductSchema.tsx` | Individual product pages (`/products/[id]`) × 3 languages | Always — even for price=0 |
| `ProductsListSchema.tsx` | Products listing page (`/products`) | Always — even for price=0 |
| `CollectionPageSchema.tsx` | Category & concern pages | Only when price > 0 (correct) |

Products with `price = 0` or `isPriceOnRequest = true` (professional devices, price-on-request items) were generating `@type: Product` with `"price": 0` in the offers — Google considers this invalid.

The 236 invalid items came from:
- Product detail pages (en/ar/ru) for zero-price products
- Products listing page including all products without price filtering

### Changes Made

**`components/schema/ProductSchema.tsx`** — Added early return guard:
```typescript
if (!product.price || product.price <= 0 || product.isPriceOnRequest) {
  return null  // No Product schema for items without valid price
}
```

**`components/schema/ProductsListSchema.tsx`** — Added filter before generating ItemList:
```typescript
const validProducts = products.filter(p => p.price > 0 && !p.isPriceOnRequest)
```

Only `validProducts` are now mapped into the `ItemList` entries.

### What Was NOT Changed

- Product pages still render normally (images, descriptions, add-to-cart, etc.)
- These schema components only generate invisible `<script type="application/ld+json">` tags
- No UI, cart, checkout, login, or payment logic was touched
- Products with valid prices are unaffected — their schema remains complete

### Why Safe

`ProductSchema` and `ProductsListSchema` are **purely SEO metadata** — hidden JSON-LD script tags read only by Google's crawler. Returning `null` from a React component renders nothing. The actual product UI is rendered by separate components (`ProductPageClientRefactored`, `ProductsPageClient`).

### Problem

**Files changed:**

## 4. Review Snippets — 290 Invalid Items

### Problem

Google Search Console **Enhancements → Review snippets** reported **290 invalid items** with 2 critical issues:

| Issue | Items |
|-------|-------|
| Invalid object type for field `<parent_node>` | 290 |
| Multiple reviews without aggregateRating object | 290 |

### Root Cause

**`components/schema/AggregateRatingSchema.tsx`** was generating invalid structured data:

1. **Invalid root type:** Used `@type: AggregateRating` as the root JSON-LD type — Google does not allow `AggregateRating` as a standalone root. It must be nested inside a valid parent (`Product`, `LocalBusiness`, etc.)
2. **Multiple reviews without aggregateRating:** The component placed `Review` objects inside `AggregateRating` instead of the other way around. The correct structure is: `Parent → aggregateRating + review[]`
3. **Fabricated reviews:** The component contained 5 hardcoded fake reviews with fictional authors ("Dr. Sarah Ahmed", "Maria Santos", etc.) and a fabricated `ratingValue: 4.8` / `reviewCount: 127`. Google explicitly penalizes fabricated review data.

The component was already removed from the barrel export (`components/schema/index.ts`) and was not actively imported anywhere, but:
- Google had already crawled and cached the invalid schema from when it was active
- The 290 errors represent cached entries across multiple pages × languages

**`components/schema/LocalBusinessSchema.tsx`** also contained fabricated `aggregateRating`:
```json
"aggregateRating": {
  "@type": "AggregateRating",
  "ratingValue": "4.8",
  "reviewCount": "127"
}
```
This was structurally valid (nested inside `LocalBusiness`) but the data was fabricated — no real review system exists.

### Changes Made

1. **Deleted `components/schema/AggregateRatingSchema.tsx`** — Removed the file entirely to prevent accidental re-use. The file was already not imported anywhere.

2. **Removed fabricated `aggregateRating` from `LocalBusinessSchema.tsx`** — Removed the fake 4.8 rating / 127 reviews. Added a comment noting it should be re-added when a real review system is implemented with actual user data.

### Why Safe

- `AggregateRatingSchema` was already not imported by any component — deleting the file changes nothing in the rendered output
- Removing `aggregateRating` from `LocalBusinessSchema` removes one hidden JSON-LD property — no visual or functional impact
- No UI, cart, checkout, login, or payment logic was touched

### When to Re-add

When a real review/rating system is implemented:
1. Add `aggregateRating` back to `LocalBusinessSchema.tsx` with data from the database
2. Optionally add `review` arrays with real user reviews
3. Ensure `aggregateRating` is always nested inside a valid parent type (`Product`, `LocalBusiness`, `Organization`)
4. Never use standalone `@type: AggregateRating` as a root schema

## 7. Product Gallery Images — POWER SOLUTION CVS (Product #5)

### Problem

After adding gallery images (`cvs_big1.jpg`, `cvs_big2.jpg`) to product ID `5` ("POWER SOLUTION CVS") via the static `lib/products.ts` file, the images did **not appear** on the live site after hard refresh.

### Root Cause

**The live site loads all product data from the PostgreSQL database (via Prisma), not from the static `lib/products.ts` file.** The static file serves only as a seed/fallback reference.

The product's `images` column in the database was `null`, which meant only the single `image` field (`/images/CVS.jpg`) was displayed. The static file change (commit `09e555ba`) had no effect on production.

### Changes Made

1. **Updated the `images` field in the production database** (direct SQL via `pg`):
   ```sql
   UPDATE products SET images = '["\/images\/CVS.jpg","\/images\/Second\/cvs_big1.jpg","\/images\/Second\/cvs_big2.jpg"]'
   WHERE id = '5';
   ```

2. **Set `productNumber` to `'5'`** — was previously `null`, now consistent with the static data and enables lookup by both `id` and `productNumber`.

3. **Static file `lib/products.ts`** was already updated (commit `09e555ba`) for consistency — both database and static data now match.

### Image Files

All three images already existed in `/public/images/`:
- `/images/CVS.jpg` (primary — already in use)
- `/images/Second/cvs_big1.jpg` (new gallery image)
- `/images/Second/cvs_big2.jpg` (new gallery image)

### How Product Images Work

The product page (`app/products/[id]/page.tsx`) renders images via:
1. `getProductByIdCached(id)` → fetches from **database** (Prisma Accelerate → Neon PostgreSQL)
2. `product.images` is a JSON string array — parsed to display a gallery carousel
3. If `images` is `null`, only the single `product.image` is shown
4. The page uses `force-dynamic` and `revalidate = 0` — changes are visible immediately

### Key Lesson

> **Always update product data in the database, not just `lib/products.ts`.** The static file is for seeding/reference only. Production data comes exclusively from PostgreSQL via Prisma.
